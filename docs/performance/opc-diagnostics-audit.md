## Minimal shared JVM sampling design

Keep one common, pure-Java immutable raw snapshot and bean reader in the existing performance architecture. It needs monotonic capture time and wall-clock timestamp; heap used/committed/max, nonheap used, physical total/free, processor count, cumulative GC collection milliseconds, and process CPU load. Cache MXBeans and heap-pool names. A <=1-second lazy raw-snapshot cache can avoid duplicate coincident RAM/diagnostic reads without a new executor or tick subscriber.

The two consumers have different cadence and history semantics:

- RAM: `RamAdvisorService.java:12,32,44-47` starts with a sample and then checks a monotonic one-second interval on PostTick. `RamSample` includes committed heap/nonheap/physical memory and a wall timestamp. Its existing optional unavailable fields are normalized to zero. Keep its existing bounded history, confidence, reset command and GC-event stream.
- Diagnostics: `PerformanceDiagnosticsConfig.java:34-35` samples every100 ticks by default (range20-1200), plus start/stopping/stopped. `JvmPerformanceSample` has used/max heap, processors, cumulative GC, process CPU load and interval GC fraction. Negative fields mean unavailable. Preserve an instance-local previous cumulative-GC value and previous *raw capture time* so each adapter computes the delta over its own actual sampling window. Sharing RAM's one-second GC fraction would silently change the default diagnostics window from about five seconds to one second.
- `GcMonitor` cannot be replaced by polling. Event duration, after-GC heap and cause/action are necessary for the existing recommendation engine; cumulative collection millis cannot reconstruct them. Notification duration must not be relabeled exact stop-the-world pause.

Use the snapshot's actual timestamp when a cached value is reused. Start/reset/lifecycle boundaries reset consumer delta baselines. End-of-life sampling may request a fresh snapshot, preserving current final-report behavior. A shared raw sampler can be process-wide because its immutable data holds no world/server references; session history and GC listener ownership must still end with the server lifecycle. A dedicated client does not gain remote-server metrics from its own JVM. Preserve old public records/adapters rather than moving or deleting public APIs solely for branding.

## Concrete safe improvements and constraints

1. Consolidate AsyncComputeManager onto AsyncTaskManager as the parent plans, retaining bounded secondary admission and result handling without a second physical CPU pool. Do not count DataWorkerPool twice: it already borrows shared CPU. Preserve the public submit/callback surface for external integrations.
2. Report CPU, IO and retired pool capacities/active/queued totals together. Defaults are CPU=processors-1 (config range1-64) and IO=max(4, CPU*2) (`AsyncThreadingConfig.java:25-31`, `AsyncTaskManager.java:68-69`). At configured CPU64, declared pools allow64CPU+128IO; workers are lazy with idle expiry, so this is capacity, not observed concurrency or a measured defect.
3. Retired executors preserve accepted tasks after reload (`AsyncTaskManager.java:81-108,436-442`). Repeated reloads can overlap many still-running pools. Any cap/reload coalescing must retain required I/O; do not solve it with silent shutdownNow, discarded futures, or caller-thread fallback. Aggregate shutdown should remain a bounded policy, with persistence behavior documented.
4. Bound manual GPU session retention before promoting it as generally bounded: `GpuProfiler.SNAPSHOTS` appends a full copied snapshot per command (`:255-257,455`); resource/class caches and `GpuDiagnostics.GPU_TIMINGS`/scope aggregates lack explicit cardinality caps (`GpuProfiler.java:52-55,360,556`; `GpuDiagnostics.java:44-45,346,458`). Samples and transient timer/debug rings are already bounded. Add explicit truncation/drop counters if limits are introduced; never silently misstate complete attribution.
5. Consider render-thread GPU cleanup on client stopping. The subscriber currently exposes only command and frame event hooks; stop explicitly removes debug callback and timer resources (`GpuDiagnostics.java:98-104`). Preserve deliberate cross-world client profiling if intended; server stopping must not own a client GL session.
6. Keep saveDrain opt-in and fail closed. `SavingCoordinator.java:116-139` uses native readiness and write-observation barriers. `:153-164` re-marks failure; `:178-186` re-marks unfinished writes before native final save. Never off-thread serialize mutable chunks, replace dirty metadata with an authoritative dirty set, force-load chunks, or claim pending success before native future completion.
7. Keep the registry conservative. Current supported IDs: c2me/c2me_*; shinoyuki_betterautosave/betterautosave; smoothchunk; fastasyncworldsave; lithium/canary/radium; modernfix; ferritecore; scalablelux/starlight; sodium/embeddium; immediatelyfast (`PerformanceOwnershipRegistry.java:21-35`). Presence-only data cannot identify an unknown mod's invasive patches. Existing feature-specific Sodium/Embeddium/Iris/Sable compatibility remains feature-owned and must not be removed as duplicate core detection.
8. The current quest close may spend up to five seconds pumping terminal handle release (`QuestServerSession.java:258-266`). This is a visible bounded shutdown contributor, not proof of an affected instance's delay. Preserve lease safety; improve reports first before changing required persistence semantics.

## Existing tests and evidence boundary

Inspected tests include `async/AsyncTaskManagerTest` (saturation rejects without caller execution; reload preserves callbacks; stale results cannot cross server lifecycle), `ExecutorShutdownTest` (all pools drain together under one deadline), `diagnostics/performance/PerformanceOwnershipRegistryTest` (save veto, unknown owner, C2ME family and complementary renderer distinctions), `saving/coordinator/DirtyChunkIndexTest` (coalescing, bounded overflow, generations, failure dirty retention, time admission, unload safety), `gpuprofiler/client/GpuFormatEstimatorTest`, and the four `loading/*Test` classes. No RAM-specific test class was found in `src/test/java`.

`saving/coordinator/CoordinatorSaveGameTests.java:30` verifies native chest-data persistence and simulated failure leaves dirty state for ordinary retry. This is useful native integration coverage; it does not prove arbitrary modpack compatibility, safe recovery from a native crash, or shutdown speedup.

`build.gradle:831` defines `loadingProfilerTest`; `:843` defines `performanceDiagnosticsTest`, which includes diagnostics, performance, saving, async, loading and relevant architecture/config/mixin tests. The parent owns serialized validation. This audit ran none of them. Meaningful new JVM-sampling coverage would assert raw-cache reuse, unavailable sentinel mapping, independent GC windows, lifecycle reset and listener cleanup; meaningful worker consolidation coverage would prove both old APIs use the same bounded physical executor, rejecting overflow without caller work and rejecting stale application after lifecycle shutdown.

Live acceptance remains separate: affected-pack before/after CPU/thread/queue data, first-world and existing-world loading, Save & Quit, integrated-world restart, dedicated server, optional optimization-mod combinations, GL driver counter availability, GPU timer/debug callback cleanup, and two-client synchronization cannot be established by this source audit.
